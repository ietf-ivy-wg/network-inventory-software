        A YANG Network Data Model of Network Inventory Software
            draft-ietf-ivy-network-inventory-software-latest

Abstract

   This document extends the base Network Inventory YANG model to
   support software-based network elements (NEs) and software
   components.  The extension introduces software lifecycle status that
   distinguishes running software from software that is installed but
   not running, together with installation timestamps for non-running
   software, and both installation and activation timestamps for running
   software.

1.  Introduction

   The Network Inventory consists of the physical and software-based
   network elements (NEs), hardware components, firmware components, and
   software components on a managed network domain.  The software-based
   network elements (NEs) are network devices that support network
   protocols and functions, e.g., routers, firewalls, and controllers,
   which can reside in any network or compute environment.

   [I-D.ietf-ivy-network-inventory-yang] defines the base Network
   Inventory YANG model for physical network element (NE) and hardware
   components of NEs.  Examples of hardware components could be rack,
   shelf, slot, board and physical port.

   The management of software-based NE and software components
   information is similar to the management of physical NE and hardware
   information.  For example, inventory data, including product names,
   serial numbers, etc. are also applicable.  This document defines a
   network inventory software YANG model.  In addition to inheriting the
   common inventory attributes of the base network inventory model, this
   document also adds some software-specific attributes of software-
   based NEs (such as controllers, virtual routers, and virtual
   firewalls) and software components (such as operating system,
   software modules, BIOS, and boot loader).

   The Network Inventory software model is classified as a network model
   (Section 4 of [RFC8309]).

   The YANG data model in this document conforms to the Network
   Management Datastore Architecture (NMDA) defined in [RFC8342].

2.  YANG Data Model for Network Inventory Software Overview

2.1.  Relationship to Other YANG Data Models

   The base network inventory model supports the software versions of
   NEs and software versions of hardware components.  This document adds
   more software component identifiers (e.g., platform OS), software NE
   type, and software lifecycle status and time stamp information to
   provide extended software information on the NE to facilitate
   software compatibility check.

   Figure 1 depicts the relationship between the network inventory
   software model and the base network inventory model.  The network
   inventory software model adds more software specific attributes.

2.2.  Network Inventory Software Tree Diagram

   The tree diagram in Figure 2 provides an overview of the data model
   for "ietf-network-inventory-software" module.

   The model applies software extension attributes at two levels:

   *  NE-level "software-rev": Describes the main system software
      revision of the network element, such as the network operating
      system release of the whole device.  Only running software is
      reported here, consistent with the base model.  The augmented
      nodes include installation-time and activation-time.

   *  Component-level "software-rev": Describes the independent software
      or firmware revision of an individual component, such as a line
      card software, a line card firmware, or a pluggable software
      module.  Only running software is reported here, consistent with
      the base model.  The augmented nodes include installation-time and
      activation-time.

   In addition, the model introduces:

   *  "installed-software": Lists at both NE and component levels,
      reporting software that is present on the entity but not currently
      running (installed, or activated but pending reload).  installed-
      software carries name, revision, status, installation-time.
      Activation-time is not modeled for installed-software entries;
      activation-time is only available once the software becomes
      running and appears in software-rev.

      module: ietf-network-inventory-software

        augment /nwi:network-inventory/nwi:network-elements
                  /nwi:network-element/nwi:software-rev:
          +--ro installation-time?   yang:date-and-time
          +--ro activation-time?     yang:date-and-time
        augment /nwi:network-inventory/nwi:network-elements
                  /nwi:network-element:
          +--ro installed-software* [name revision]
             +--ro name                 string
             +--ro revision             string
             +--ro status?              identityref
             +--ro installation-time?   yang:date-and-time
        augment /nwi:network-inventory/nwi:network-elements
                  /nwi:network-element/nwi:components/nwi:component:
          +--ro installed-software* [name revision]
             +--ro name                 string
             +--ro revision             string
             +--ro status?              identityref
             +--ro installation-time?   yang:date-and-time
        augment /nwi:network-inventory/nwi:network-elements
                  /nwi:network-element/nwi:components/nwi:component

2.3.  Software-based Network Elements

   In the base Network Inventory YANG model, "ne-type" is a YANG
   identity that describes the type of the network element and only the
   "ne-physical" identity" is defined.  This document adds "ne-software-
   based" identity for software-based NEs.

   The base Network Inventory model also defines common inventory
   attributes, including the software version, patch versions, product
   name, and serial number.  The data is also applicable to software-
   based NEs.

   A software-based NE performs network protocol or forwarding functions
   but does not correspond to a distinguishable hardware chassis.  It
   may be hosted on bare-metal server, in a virtual machine, container,
   or cloud compute instance.

2.4.  Software Components

   Software components refer to the software installed on the NE, such
   as operating system, software modules, BIOS, and boot loaders.

   Similar to the common inventory attributes of NEs, the common
   attributes of software components (such as software revisions, patch
   revisions, product name, and serial number) are also applicable to
   software components.  For software revisions and patch revisions, the
   base inventory (Section 4 of [I-D.ietf-ivy-network-inventory-yang])
   defines the "list" of "software-rev" and the "list" of "patch".  For
   example, on a router, software components may include a routing
   protocol package (e.g., "foo-rt-protocol-suite"), or a firmware
   module for a line card (e.g., "foo-lc-fw-21.5.3").

   The base "software-rev" list reports software that is currently
   running on the entity.  Software that is present but not running
   (e.g., installed but not activated, or activated but pending a reload
   for a cold patch or cold upgrade) is reported in the "installed-
   software" list defined by this document.  The two lists are mutually
   exclusive: an entry MUST NOT appear in both lists at the same time.

4.  Operational Considerations

   This section complements the operational considerations of the base
   network inventory model [I-D.ietf-ivy-network-inventory-yang].  The
   considerations of [I-D.ietf-ivy-network-inventory-yang] also apply to
   this extension: the read-only perspective of inventory data, data
   discovery by the server from underlying elements, aggregation at
   hierarchical controller interfaces, and brownfield migration
   scenarios.

   This model provides read-only reporting of software status and
   associated timestamps.  It reflects the state of software revisions
   and patches as discovered by the server; it does not track software
   configuration intent or repository state.

   The model is not intended to expose every internal software component
   present on the network element.  It only covers operator-relevant,
   separately versionable and independently upgradable software
   artifacts, such as base OS images, line-card FPGA firmware, separable
   feature modules, and hotfix patches.  Embedded static libraries and
   fine-grained internal sub-components that cannot be independently
   managed or upgraded are out of scope.

   The base 'software-rev' list reports running software only.  Presence
   of an entry in 'software-rev' implies that the software is running.
   The 'installed-software' list reports software that is present but
   not running, including software that is installed but not activated,
   and software that has been activated but is pending a reload (cold
   patch or cold upgrade).

   Full software lifecycle management (install, activate, rollback,
   remove operations, etc.) is out of scope of this document and could
   be defined in separate YANG modules.

5.  Security Considerations

   This section is modeled after the template described in Section 3.7
   of [RFC9907].

   The "ietf-network-inventory-software" YANG module augments the base
   network inventory model defined in
   [I-D.ietf-ivy-network-inventory-yang].  All security considerations
   specified in the base model apply to this extension module.  This
   section complements the base model with additional security
   considerations specific to inventory software extensions.

   The "ietf-network-inventory-software" YANG module defines a data
   model that is designed to be accessed via YANG-based management
   protocols, such as NETCONF [RFC6241] and RESTCONF [RFC8040].  These
   YANG-based management protocols (1) have to use a secure transport
   layer (e.g., SSH [RFC4252], TLS [RFC8446], and QUIC [RFC9000]) and
   (2) have to use mutual authentication.

   The Network Configuration Access Control Model (NACM) [RFC8341]
   provides the means to restrict access for particular NETCONF or
   RESTCONF users to a preconfigured subset of all available NETCONF or
   RESTCONF protocol operations and content.

   Some of the readable data nodes in this YANG module may be considered
   sensitive or vulnerable in some network environments.  It is thus
   important to control read access (e.g., via get, get-config, or
   notification) to these data nodes.

   Specifically, the following subtrees and data nodes have particular
   sensitivities/vulnerabilities:

   *  "/nwi:network-elements/nwi:network-element/nwi:software-rev"

   *  "/nwi:network-elements/nwi:network-element/nwi:software-rev/
      nwi:patch"

   *  "/nwi:network-elements/nwi:network-element/nwis:installed-
      software"

   *  "/nwi:network-elements/nwi:network-
      element/nwi:components/nwi:component/nwi:software-rev"

   *  "/nwi:network-elements/nwi:network-
      element/nwi:components/nwi:component/nwi:software-rev/nwi:patch"

   *  "/nwi:network-elements/nwi:network-
      element/nwi:components/nwi:component/nwis:installed-software"

   These extensions add installation and activation timestamps for
   running software, plus a separate installed-software list for both
   NE-level and component-level.  Disclosure of detailed software
   versions, patch levels, and lifecycle timestamps can reveal unpatched
   vulnerabilities and operational maintenance windows, enabling
   targeted attacks.

Appendix A.  Examples of Software Attributes

   This appendix illustrates, by means of four typical scenarios, how to
   populate the software-specific nodes defined in "ietf-network-
   inventory-software".

   Scenario 1: Whole-device base software (example-os) running, with a
   hot patch (P3) already running and a hot patch (P4) installed but not
   yet activated.  A line-card programmable forwarding image (example-
   fpga-image) is running, with a cold patch (2.1.0.P1) administratively
   activated and pending reload.  An independent telemetry software
   module (telemetry-module) is running, with a newer revision (1.6.0)
   installed but not yet activated.

   Scenario 2: Whole-device cold upgrade, where a new base software
   revision (8.0.0) has been installed and is pending reload.

   Scenario 3: Software-based virtual router running its base software
   (vrouter-os) with an active hotfix (Hotfix-05), and a newer base
   revision (24.06) installed but not yet activated.

   Scenario 4: Whole-device base software (example-os) running, with an
   independent hotfix (os-hotfix-P5) modelled as a separate top-level
   software-rev entry.
